# Lab Devices Client — Windows Service & Control Panel

**Date:** 2026-04-27
**Status:** Approved (brainstorming complete; pending spec review before plan)
**Builds on:** [`2026-04-26-lab-devices-client-design.md`](./2026-04-26-lab-devices-client-design.md)
**Target platform:** Windows (amd64); cross-compile from macOS continues to work.

## 1. Purpose

Repackage the existing single-binary client so a lab operator can install it as a long-running Windows service from a small native control panel. The panel is the only UI surface: it shows whether the service is installed and running, displays the current config (with a validation warning if it's broken), and offers Install / Uninstall / Restart buttons plus shortcuts for opening the config and log files.

This is a packaging and operational change, not a behavioral one. The chisel reverse tunnel, REST API, discovery, and serial-IO behavior described in the prior spec are unchanged.

## 2. Run modes — single binary, multiple personas

One `.exe` (one icon, one artifact). At process start, `cmd/lab_devices_client/main.go` dispatches based on context:

| Detected as                                 | How                                            | Behavior                                                                                                                                            |
| ------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Started by SCM                              | `svc.IsWindowsService()` returns true          | **Service mode.** Runs the chisel/REST/discovery logic, file-logged via lumberjack, honors SCM Stop/Shutdown.                                       |
| `--admin-action=<install\|uninstall\|restart>` | argv flag                                    | **Admin-action mode.** Performs the requested SCM operation and exits. Only ever spawned by the panel as an elevated child via `ShellExecuteEx "runas"`. |
| `--foreground`                              | argv flag                                      | **Foreground mode.** Existing pre-service behavior — runs the app with stdout JSON logs, signal-based shutdown. Developer convenience.              |
| Anything else (e.g. double-click)           | default                                        | **GUI mode.** Opens the walk control panel.                                                                                                         |

Only three flags exist: `--admin-action`, `--error-file` (paired with the former), `--foreground`. Anything else is a usage error.

### 2.1 Subsystem & console behavior

The binary is built with `-ldflags="-H windowsgui"` so double-clicking does not flash a console window. Foreground mode calls `windows.AttachConsole(ATTACH_PARENT_PROCESS)` (from `golang.org/x/sys/windows`) so its stdout/stderr land in the calling cmd.exe / PowerShell when invoked from one. When launched without a parent console (double-click + `--foreground`, an unusual combination), output goes nowhere — that's expected; foreground is a developer affordance.

**`app.Run(ctx, cfg) error`** is the unified shutdownable runner used by service, foreground, and any future test harness. It contains the body of the existing `cmd/lab_devices_client/main.go::run()` minus config loading and minus logger configuration, both of which move to the caller (different callers want different sinks).

## 4. Service worker (`internal/winsvc/worker.go`)

`winsvc.RunWorker()` is called from `main` when `IsWindowsService()` is true. It:

1. Resolves the config path (`<dir of os.Executable()>/lab_devices_client_config.yaml`).
2. Configures `slog.SetDefault` with a `slog.NewJSONHandler` writing to `<dir of os.Executable()>/lab_devices_client.log` via `*lumberjack.Logger{MaxSize: 10, MaxBackups: 3, LocalTime: true, Compress: false}`. (See §8.)
3. Calls `svc.Run("LabDevicesClient", &handler{})`.

The handler's `Execute(args, r, changes)` method:

1. `changes <- svc.Status{State: svc.StartPending}`
2. Loads + validates config. **On failure:** logs the error, sends `svc.Stopped` with a non-zero `Win32ExitCode`, returns. SCM marks the service as failed; the panel shows `Stopped`; the operator opens the log to find why.
3. Spawns a goroutine running `app.Run(ctx, cfg)`. The context is cancellable from the handler.
4. `changes <- svc.Status{State: svc.Running, Accepts: AcceptStop|AcceptShutdown}`.
5. Loops on the request channel:
   - `svc.Interrogate` → echo current status.
   - `svc.Stop` / `svc.Shutdown` → `changes <- StopPending`, cancel context, wait up to 30 s for the `app.Run` goroutine to return. Whether it returned cleanly or timed out, send `Stopped` and exit.

**Restart-on-failure** is not configured at install time for v1. If the service exits abnormally, it stays Stopped until the operator restarts it from the panel. (We can add `mgr.RecoveryActions` later without redesign.)

**Steady-state errors** (chisel reaching its retry budget, REST listener dying, etc.) bubble up exactly as they do in the current code: `app.Run` returns an error, the worker sends `Stopped`, and the operator sees the service in the Stopped state on next poll.

## 5. Panel UI (`internal/panel`)

A single fixed-size walk window, ~480×360 px, no resize handles.

```
┌─ Lab Devices Client ──────────────────────────────────┐
│                                                       │
│  Status:  ●  Running                                  │
│                                                       │
│  ─── Configuration ─────────────────────────────────  │
│  Chisel server:    111.88.145.138:7000                │
│  Remote port:      8081                               │
│  REST port:        0 (auto)                           │
│  Discovery:        include=[], exclude=[]             │
│  Log level:        info                               │
│                                                       │
│  ⚠ chisel.remote_port must be in 1..65535             │
│                                                       │
│  [ Install ] [ Uninstall ] [ Restart ]                │
│  [ Open config file ] [ Open log file ]               │
│                                                       │
│  Service installed at 12:34:56                        │  ← status bar
└───────────────────────────────────────────────────────┘
```

### 5.1 Polling loop

A 1 s `walk.Timer` does two things on each tick:

1. **Re-read the config file from disk** via `config.LoadPartial(path)` (see §7). Manual edits surface immediately.
2. **Query SCM for the service state** via `mgr.Connect → m.OpenService("LabDevicesClient") → s.Query()`. If the service does not exist, treat as `Not installed`. If SCM/Open transiently fail (rare), keep the previous state so the indicator does not blink.

Both are cheap; both run on the GUI thread. No background goroutines beyond the elevated-child wait described below.

### 5.2 Status indicator

One label with a colored dot:

| Service state          | Color  |
| ---------------------- | ------ |
| Running                | green  |
| Starting / Stopping    | yellow |
| Stopped                | grey   |
| Not installed          | grey   |
| Config invalid (Not installed only) | red |

### 5.3 Button enable rules

| Service state         | Install                       | Uninstall | Restart |
| --------------------- | ----------------------------- | --------- | ------- |
| Not installed         | enabled iff config valid      | disabled  | disabled |
| Stopped               | disabled                      | enabled   | enabled  |
| Running               | disabled                      | enabled   | enabled  |
| Starting / Stopping   | disabled                      | disabled  | disabled |

`Open config file` is always enabled. `Open log file` is enabled iff the log file exists.

These rules live in `panel/state.go` as a pure function `func ButtonState(svcState svc.State, cfgValid bool) (install, uninstall, restart, openLog bool)` and are unit-tested with a table.

### 5.4 Validation surfacing

On every poll tick, `config.LoadPartial(path)` returns `(Config, error)`. The `Config` is populated best-effort from whatever fields parsed; the `error` is the first validation failure. We render the field values from the returned `Config` and, if `error != nil`, render the error string in red below the config block and disable Install. (See §7 for the partial-parse semantics.)

### 5.5 First-run scaffold

On `panel.Run()` start, if the config file does not exist, we call `config.WriteScaffold` to create it, then proceed normally. The panel displays the scaffolded values; whether a validation warning appears depends on whether the scaffold's defaults are valid (current scaffold parses cleanly).

The service worker does **not** write a scaffold. If the service starts and the config file is missing, it logs the error and exits with `Stopped`. The GUI is the natural first-run surface; the service should not second-guess admin choices.

### 5.6 Button handlers

**Install / Uninstall / Restart** all share one helper:

1. Disable all admin buttons; status bar reads "Working…".
2. Build a temp error-file path: `%TEMP%\lab_devices_client_admin_<panel_pid>.err`.
3. `ShellExecuteEx` with:
   - `lpVerb`: `"runas"` (UAC prompt happens here)
   - `lpFile`: `os.Executable()`
   - `lpParameters`: `--admin-action=<name> --error-file=<path>`
   - `fMask`: `SEE_MASK_NOCLOSEPROCESS` (so we get a process handle to wait on)
4. `WaitForSingleObject` on the returned process handle.
5. Read the error file. If non-empty, show its contents in a `walk.MsgBox` with icon `MsgBoxIconError`. If empty, status bar reads e.g. "Service installed at 12:34:56".
6. Delete the temp error file.
7. Re-enable buttons (next poll tick refreshes their state from current SCM status anyway).

If `ShellExecuteEx` returns `ERROR_CANCELLED` (operator declined the UAC prompt), no MessageBox; status bar reads "Cancelled."

**Open config file** / **Open log file:** `ShellExecute` with `lpVerb="open"` and the absolute path. Default handler (Notepad for `.yaml` and `.log`) opens the file.

### 5.7 Window close

Closing the window exits the GUI process. The Windows service is unaffected — it is owned by SCM in a separate process.

### 5.8 Single-instance

Not enforced. If the operator opens the panel twice, both poll the same SCM and show consistent state. Simultaneous Install clicks would have one succeed and the other report "service already installed" — annoying but not dangerous.

## 6. Admin-action subprocess (`internal/winsvc/control.go`)

The dispatcher in `main.go` calls `winsvc.RunAdminAction(action, errorFile) int` when `--admin-action` is set. The function returns an exit code (0 = OK, 1 = error). On error, before exiting, it writes the error message UTF-8 to `errorFile`. The panel reads that file after `WaitForSingleObject` and surfaces its contents.

A temp file is used (rather than stderr or just an exit code) because `ShellExecuteEx "runas"` does not pipe stdio across the UAC boundary. The pre-allocated path lets the elevated child write rich error text without IPC plumbing.

```go
func RunAdminAction(action, errorFile string) int {
    err := func() error {
        m, err := mgr.Connect()
        if err != nil { return fmt.Errorf("connect SCM: %w", err) }
        defer m.Disconnect()

        switch action {
        case "install":   return install(m)
        case "uninstall": return uninstall(m)
        case "restart":   return restart(m)
        default:          return fmt.Errorf("unknown action %q", action)
        }
    }()
    if err != nil {
        os.WriteFile(errorFile, []byte(err.Error()), 0o644)
        return 1
    }
    return 0
}
```

### 6.1 `install`

1. `exePath, _ := os.Executable()` — the absolute path of *this* (running, elevated) .exe is what SCM will invoke on every service start.
2. Service config:

   | Field                | Value                                                                     |
   | -------------------- | ------------------------------------------------------------------------- |
   | Service name         | `LabDevicesClient`                                                        |
   | Display name         | `Lab Devices Client`                                                      |
   | Description          | `Exposes serial-port lab devices via chisel reverse tunnel.`              |
   | `ServiceType`        | `SERVICE_WIN32_OWN_PROCESS`                                               |
   | `StartType`          | `SERVICE_AUTO_START`                                                      |
   | `ErrorControl`       | `SERVICE_ERROR_NORMAL`                                                    |
   | `ServiceStartName`   | `""` (empty = LocalSystem; no password to manage)                         |
   | `BinaryPathName`     | `exePath` (no extra args; SCM passes none, dispatcher detects via `IsWindowsService`) |

3. `m.CreateService("LabDevicesClient", exePath, cfg)`. If the OS returns `ERROR_SERVICE_EXISTS`, return the friendly message "Service already installed."
4. After create, immediately call `s.Start()`. If start fails, leave the service installed (operator can fix config and click Restart) and return the start error so the panel surfaces it.

### 6.2 `uninstall`

1. `m.OpenService("LabDevicesClient")`. On `ERROR_SERVICE_DOES_NOT_EXIST` → friendly error: "Service is not installed."
2. Query state. If running, `s.Control(svc.Stop)` and poll `s.Query` up to 15 s waiting for `Stopped`. Timeout → return error "Service did not stop within 15 s; check the log file or kill the process manually." (15 s is intentionally longer than the worker's normal teardown — closing serial ports + chisel typically completes in well under a second — but shorter than the worker's 30 s self-imposed grace, so the panel surfaces a stuck shutdown before SCM forces the worker dead.)
3. `s.Delete()`. Deletion takes effect when the last handle closes; canonical pattern is `defer s.Close()` after Delete. The handle to `s` is closed when the function returns, completing the deletion.

### 6.3 `restart`

1. `m.OpenService(...)`. Missing → friendly error.
2. If state ∈ {Running, StartPending}: Stop, poll up to 15 s for Stopped (same reasoning as §6.2).
3. `s.Start()`. Poll up to 15 s for `Running` or `StartPending`.
4. If still Stopped after 15 s, return: "Service failed to start; check log file." (The actual reason is in `lab_devices_client.log` — config errors, bind errors, etc. are logged before the worker exits.)

### 6.4 Idempotency & safety

None of the three actions are blindly destructive. Each queries state first and returns a clear error rather than overwriting. Re-running Install when already installed gives "Service already installed", not silent re-creation. Re-running Uninstall when already uninstalled gives "Service is not installed".

No automatic retries inside admin actions — a failure bubbles a useful error and the operator decides next steps.

## 7. Config — partial parse for the panel

The current `config.Load(path) (Config, error)` returns `(zero, err)` on the first validation failure. The panel needs the parsed-but-invalid values to display them, so we add a sibling:

```go
// LoadPartial parses path and returns whatever fields were populated, plus
// the first validation error (or nil if valid). Distinct from Load, which
// returns a zero Config on validation failure.
func LoadPartial(path string) (Config, error)
```

Implementation: read the file, `yaml.Unmarshal` into a `Default()` baseline (so missing fields keep their defaults), call `Validate(&c)`, return `(c, err)`. If YAML parsing itself fails (malformed file), return `(Default(), err)`.

`Load` keeps its current strict semantics for the service worker: bad config → no service. The panel uses `LoadPartial`. No other call sites change.

## 8. Logging

- **Service mode:** `slog` JSON handler over `*lumberjack.Logger` writing to `<dir of os.Executable()>/lab_devices_client.log`. Settings: `MaxSize: 10` MB, `MaxBackups: 3`, `Compress: false`, `LocalTime: true`. Adds dep `gopkg.in/natefinch/lumberjack.v2`.
- **Foreground mode:** `slog` JSON handler over stdout (existing behavior, unchanged).
- **GUI mode and admin-action mode:** no logs. Admin-action errors are surfaced via the temp error file.

The log file lives next to the .exe so the operator (or whoever they ship the file to for triage) can find it without poking around `%ProgramData%` or `%LOCALAPPDATA%`.

## 9. Build

`Taskfile.yaml` gains a `resource` step that compiles a `.syso` via `goversioninfo`:

```yaml
tasks:
  resource:
    cmds:
      - go run github.com/josephspurrier/goversioninfo/cmd/goversioninfo@latest \
          -64 -o cmd/lab_devices_client/resource_windows.syso \
          -icon=assets/icon.ico assets/version.json

  build:
    deps: [resource]
    cmds:
      - mkdir -p {{.OUTPUT_DIR}}
      - GOOS={{.GOOS}} GOARCH={{.GOARCH}} go build \
          -ldflags="-s -w -H windowsgui" \
          -o {{.OUTPUT_DIR}}/{{.BINARY_NAME}} ./cmd/lab_devices_client
```

The `.syso` embeds three things:

1. **Icon** — `assets/icon.ico` (placeholder for now; swap by replacing the file).
2. **UAC manifest** — `requestedExecutionLevel="asInvoker"`, `uiAccess="false"`. This bakes the Q3 elevation policy into the binary; the panel runs in the user's session, admin actions relaunch elevated.
3. **Version info** — populated from `assets/version.json`.

`-H windowsgui` is the linker flag that selects the Windows GUI subsystem (no console window flash on double-click). `app.AttachConsole(ATTACH_PARENT_PROCESS)` is invoked at the top of `--foreground` mode so a developer running from cmd.exe still sees stdout.

Cross-compile from macOS continues to work: walk, lumberjack, and goversioninfo are all pure Go (no CGO).

The generated `cmd/lab_devices_client/resource_windows.syso` is a build artifact — added to `.gitignore`. `task build` always regenerates it (via the `resource` dep).

## 10. Tests

Most of the new code is testable on macOS; the SCM-glue and walk-rendered pieces are Windows-only and covered by manual QA.

| Area                              | Test approach                                                                                                                      |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `internal/app`                    | No new tests. Pure wiring; underlying packages (config, registry, api, …) keep their existing tests.                               |
| `internal/config`                 | Add tests for `LoadPartial`: mostly-valid file with one bad field returns the partial values plus the validation error string.     |
| `internal/panel/state.go`         | Table-driven tests for `ButtonState(svcState, cfgValid)` covering every state × cfg-valid combination.                             |
| `internal/winsvc/control.go`      | Mock the `mgr.*` calls behind a small `scmClient` interface (Connect, OpenService, CreateService, DeleteService). Tests verify install/uninstall/restart sequences against a fake. |
| `internal/winsvc/worker.go`       | Not unit-tested. Thin glue over `app.Run`. Manual QA.                                                                              |
| Panel rendering                   | Not unit-tested. Walk widgets + GUI thread. Manual QA on Windows.                                                                  |

Coverage target: **≥80%** on `config`, `panel/state.go`, and the testable subset of `winsvc/control.go`. Manual QA on a real Windows machine covers install, start, stop, uninstall, restart, config reload after edit, and behavior after a deliberately broken config.

## 11. Out of scope (v1)

- Service auto-restart on failure (`mgr.RecoveryActions`). Add later if operators report needing it.
- Code-signing the .exe. Add when distribution outside the lab matters.
- Localization of panel strings. English only.
- A "View live log" pane in the panel. Operators use the Open log file button.
- Editing config from inside the panel. Operators edit the YAML file directly.
- Per-field validation hints in the panel. The first validation error (the same one the service would hit) is enough.
- Auto-updates. Replacing the .exe is a manual operation: stop service, replace file, start service.
